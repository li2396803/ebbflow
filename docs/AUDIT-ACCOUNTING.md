## 1. 审计范围与方法

**数据底座**（只读）：

```
share(code, date, wan, src)   份额，单位「万份」
nav(code, date, nav)          单位净值，单位「元」
event(code, date, kind, ratio) 拆分/合并；ratio = 份额乘数（实测：merge 0.512 ⇒ 份额×0.512、净值÷0.512）
fund(code, name, list_date)   上市日
series_v2(sub, date, val, scale, flow, coverage)  站点 v2 口径序列（站内默认口径）
```

**独立实现**：`verify/audit/_db.mjs`（读表）、`_flows.mjs`（逐日流量/窗口/前缀和）。除"成分宇宙"（`lib/universe.mjs::loadUniverse`，属数据而非算术）外，审计脚本不 import `lib/metrics.mjs` 等实现。

**口径定义（审计基准）**，逐 ETF、逐日、以「当日份额单位 + 当日净值」计价：

```
规模_t   = S_t / 1e4 × nav_t                                  （亿元）
净申购_t = (S_t − S_{t−1} × r_t) / 1e4 × nav_t                （亿元/日）
           r_t = 当日发生的事件 ratio（无事件 = 1）
净值贡献_t = S_{t−1} × r_t × (nav_t − nav_{t−1} / r_t) / 1e4
恒等式   : 规模_t − 规模_{t−1} = 净申购_t + 净值贡献_t          （逐日精确）
```

`r_t` 只在事件当日出现，作用是"把昨天的份数换算成今天的份数"，**不能把未来事件也算进来**——这是 E1 的根源。

## 3. 净申购口径

### 3.1 三处实现，口径各不同

| 位置 | 用途 | 前值折算基准 | 计价单位 | 结论 |
|---|---|---|---|---|
| `lib/pipeline.mjs:246-248` | `series.flow` → charts / subs.flowSeries | `prevDate`（已修） | 最新份额单位 × **当日**净值 | 🔴 E1 |
| `lib/metrics.mjs:143-153`（`dailyFlow`） | `etf-ranges/*.json` 的 flow | `dates[i]`（**旧实现**） | 同上 | 🔴 E2 |
| `lib/payloads.mjs:226` | `subs.json` 里逐 ETF 的 flow | 不折算 | `Δ份额 × 末日净值` | 🟠 E3 |

### 3.2 【错误 E1】"未来事件乘数"：历史流量被整体缩放

**定义**：`makeSplitAdjuster`（`lib/metrics.mjs:67-84`）把某日份额乘上「该日之后所有事件 ratio 的乘积」换算到**最新份额单位**；随后 `pipeline.mjs:248` 又乘上**当日净值**。两个量不在同一单位（一个是"最新份数"，一个是"当日元"），数学上等价于：

```
实现值_t = (S_t·m_t − S_{t−1}·m_{t−1}) × nav_t / 1e4
        = m_t × 真实净申购_t        （当 t 无事件时）
m_t = Π {e.date > t} e.ratio          ← 未来事件的乘数，事件越早影响越大
```

只有 `m_t = 1`（即该日之后没有任何折算）时才对。**事件发生日之前的所有历史流量都被乘了 m_t。**

**采样复算（一）：159219 2025-05-15**

该 ETF 两次 `split ratio=4.851`（2025-08-14、2026-10-29）⇒ 早期 `m = 4.851² = 23.53`。

| 项目 | 数值 |
|---|---|
| 当日份额 | 17,438.80 → 7,638.80 万份 |
| 当日净值 / **当日 AUM** | 1.0131 / **0.77 亿元** |
| 站内/管道 flow（现行） | **−23.36 亿元** ← 是这只基金全部规模的 30 倍 |
| 真实净申购（当日单位） | **−0.99 亿元** |
| 比值 | 23.53 = 4.851² |

**采样复算（二）：510310 2023-12-01 → 2024-06-28（合并前）**

| 项目 | 数值 |
|---|---|
| 真实 `Σ Δ份额×nav` | **949.65 亿元** |
| 实现给出的 `Σ flow` | **486.22 亿元** |
| 比值 | 0.5120 = 合并 ratio |

对账也验证了修正公式的自洽：`Δ规模 = Σ净申购 + Σ净值贡献`，510310 的 1y/3y/5y 残差均为 **0.00**（见 `03-identity` 与 06 脚本 B 段）。

**影响面**（`node verify/audit/06-event-scaling.mjs`）：

- 有折算事件的 ETF **219 只 / 254 个事件**；乘数 m 的范围 **0.0002 – 23.53**（159777 有 6 个事件，早期历史流量被缩到 0.02%：几乎被抹掉）；
- `etf-ranges` 3y/5y 区间：431 条可比条目中 **244 条**与修正值相差 >1 亿元；
- 6 个区间全部计入：**382/1,222（31.3%）** 条目的 |误差|>1 亿元，平均 |误差| 19.6 亿元，**最大 2,870 亿元**：

| ETF | 区间 | 分片显示 | 修正值 |
|---|---|---|---|
| 510310 | 5y | **−2643.53** | **+226.35**（符号翻转） |
| 510310 | 3y | −2812.32 | −101.14 |
| 511030 | 3y | −676.78 | +382.96 |
| 515880 | 3y | +1213.94 | +471.25 |

- 小类级序列（charts / subs 下发的 `flowSeries`）：72 个小类中 **39 个**存在单日偏差 >1 亿元；半导体芯片全历史累计流量 库内 **3908 亿** vs 修正 **2804 亿**（差 1104 亿）；有 **25 个 (小类×日)** 出现符号翻转（如半导体芯片 2026-07-22：库内 +20.99 vs 修正 −2.14）。

**结论**：这是本次审计最严重的问题。它不影响"最近一个交易日"（m=1），但让**所有含折算事件的 ETF 的历史净申购、以及 3y/5y 区间净申购**失真，量级可达数十倍并可能翻转符号。

**修复（最小改动）**：把"折回当日单位"再计价，即

```js
// pipeline.mjs:246-248 与 metrics.mjs:149-151 同一处改动
const mt = adjust(code, d, 1);            // 当日之后事件的乘数（用 1 取因子）
const mp = adjust(code, prevDate, 1);
const flow = ((r.wan - p * (mp / mt)) / 1e4) * nav;   // 或 ((cur - before) / mt / 1e4) * nav
```

等价说法：**份额用最新单位时，净值也必须换成最新单位（`nav_t / m_t`），否则单位不一致。**
建议同时加一条运行期断言：`|flow_t| ≤ scale_t`（单只 ETF 单日净申购不可能超过其规模），可直接抓住 159219 这类 30 倍 AUM 的异常。

### 3.4 【错误 E3】`subs.json` 逐 ETF 的 flow 是近似值

`lib/payloads.mjs:226`：

```js
const flowE = a != null && b != null && nav != null ? ((b - a) / 1e4) * nav : null;  // b/a = 期末/期初份额，nav = 期末净值
```

即 `Δ份额(整段) × 期末净值`，而不是契约定义的"逐日 `Δ份额_t × nav_t` 求和"。7 日窗口下二者接近，但：

- 全样本 **1,649 / 1,649 只** ETF 的分片值都等于该近似式（100%）；
- 与"逐日求和"相差 **>0.02 亿的有 607 只**，最大 **54.65 亿**（沪深300/510300：分片 261.17 vs 逐日和 315.82）；
- 含折算事件的窗口会明显失真（因为完全不折算）。

**结论**：同一页面里"小类净申购"（逐日求和，正确定义）与"成分 ETF 净申购"（近似）不可加、不可对账。建议改用 `etfRanges` 的精确值（修好 E1/E2 之后），或在字段名/UI 上明确标注"近似"。

## 4. 变化率恒等式

**定义**：契约 §二 说 `规模变化率 ≈ 流量口径 + 净值涨跌幅`。严格成立的是：

```
规模变化率 = 净申购/期初规模 + 净值贡献/期初规模
净值贡献_t = S_{t−1}·r_t·(nav_t − nav_{t−1}/r_t)/1e4
```

**验证**（`node verify/audit/03-identity.mjs`）：

- 逐 ETF、数据连续时**精确成立**：510310 的 1y/3y/5y、510050 的 1y 分解残差均 **0.00 亿**；
- 510050 1y：`Δ规模 −1086.57 = Σ净申购 −1086.58 + 净值贡献 +0.01`；
- 但**"≈ 净值涨跌幅"这一步不可靠**：510050 1y 净值涨跌 **−6.50%**，而净值贡献率 ≈ **0.00pp**（因为份额从 577 亿份降到 24 亿份，后期的净值波动只作用在小余额上）。差额 6.5pp。
- 小类层面还叠加**成分变动/数据缺口**残差：5 小类 × 4 区间的最大残差 **13.7pp**（半导体芯片 1y，残差 200 亿，其中新进 16 只成分、进入日规模仅 50 亿，其余来自数据缺口）。

**结论**：恒等式的第三项应叫「**份额加权的净值贡献**」，不是「净值涨跌幅」；小类层面还必须叠加「成分变动」。建议 METRICS.md 改写为：

```
规模变化率 = 流量/期初规模 + 份额加权净值贡献/期初规模 + 成分变动残差/期初规模
并在 UI 上把第三项注明为"净值与成分变动"，不要承诺"≈ 净值涨跌幅"。
```

## 5. 裁决：区间净申购是否包含期初 T0

**结论：应当排除 T0（`flow = Σ_{i=i0+1}^{i1} flowDaily[i]`）。** 这是明确的会计判断，不是偏好问题。

### 5.1 理由

1. **基准不对称**：区间展示的"期初规模"取 `scale[i0]`（`web/js/etf-range.js:110`、`payloads.mjs` 的 `first`），而 flow 若从 `i0` 起算，就等于把 "T0−1 收盘 → T0 收盘" 的申赎算进了一个以 T0 收盘为起点的窗口。期初余额是 T0 收盘的份额，对应的资金变动应当从 T0 之后开始。
2. **相邻区间重复计量**：T0 同时是上一个区间的期末（i1）。实测（`04-t0.mjs` B 段）：1m 窗口 `2026-09-23…2026-10-23` 与 `2026-10-23…2026-11-24` 都把 `2026-10-23` 的流量计入，同一天被两个区间各算一次。
3. **对账要求**：只有排除 T0，flow 才能和「期末−期初」对上：

| 510050 1 年（2025-11-24 → 2026-11-24） | 数值 |
|---|---|
| 期末规模 − 期初规模 | −1086.57 亿 |
| 净值贡献 | +0.01 亿 |
| ⇒ 应有的净申购 | **−1086.58 亿** |
| 不含 T0（`Σ[i0+1..i1]`） | **−1086.58 亿** ✅ |
| 含 T0（现行 `Σ[i0..i1]`） | **−1071.29 亿** ❌ 差 +15.29 亿（= T0 当日流量） |

（与 Lead 给的 −1086.6 / −1071.3 完全一致。）

### 5.2 影响量级

- 期初日流量均值：1m 窗口 **0.51 亿元/只**，1y 窗口 **0.29 亿元/只**；`|期初日流量|>5 亿` 的 ETF 在 1m 窗口有 27 只。
- 极端值会让结果面目全非：`中证1000/560010` 1m 窗口期初日流量 5.22 亿，而整个区间净申购只有 0.03 亿——含 T0 时，**区间净申购几乎完全等于"期初那天"**（占比 18,614%）。

### 5.3 改哪里（四处，必须一起改）

| 位置 | 现状 | 改为 |
|---|---|---|
| `lib/metrics.mjs:170` `etfRangeMetrics` | `for (i=i0; i<=i1)` | `i=i0+1` |
| `lib/payloads.mjs:105`、`:136`（表格窗口 flow） | `for (i=first; i<=last)` | `i=first+1` |
| `lib/payloads.mjs:253`（`subs.flow`，7 日窗口） | `for (i=winIdx[0]; …)` | `winIdx[0]+1` |
| `web/js/etf-range.js:117`（自定义区间前端求和） | `sumRange(flowArr, i0, i1)` | `sumRange(flowArr, i0+1, i1)` |

同时把 METRICS.md §5.2 的"包含期初当天"改成"不含期初；期初 = 期末 − N 个月所在交易日收盘，flow 从下一交易日起算"。

> 如果坚持"含期初"，那期初规模就必须改成 `scale[i0-1]`（前一日收盘），六处一起改；二者不能混用——这正是当前的问题。

## 5. 复验中新发现的问题

### 🟠 E4 `makeSplitAdjuster` 对「多次事件」的 ETF 取错累计乘数

**位置**：`lib/metrics.mjs:76-82`

```js
for (const e of [...list].sort((a, b) => b.date.localeCompare(a.date))) {   // 降序建表
  m.set(e.date, (factor *= e.ratio ...));
}
for (const [d, v] of m) if (d > date) return wan * v;   // ← Map 按插入顺序（降序）遍历
```

`m` 的插入顺序是**日期降序**，所以 `if (d > date)` 命中的是「**最晚**的那个事件」，返回的是"最晚事件及其之后"的累计积，而不是「该日期之后**全部**事件」的积。单事件 ETF 不受影响（只有一个），**多次事件 ETF 在早期事件日的前值会被少乘**。

**证据**（`node verify/audit/09-invariant.mjs` 的对照 + 全量扫描）：

- 159219 有两个 `split 4.851`（2025-08-14、2026-10-29）：
  `adjust(2025-08-13)` 应为 4.851×4.851 = **23.53**，实际返回 **4.851**；
  于是 2025-08-14 的流量被算成 **+0.4482 亿**（应为 0——份额跳变恰好等于折算比例）；2026-10-29 才是 0。
- 涉及 **24 只 ETF**（有事件的 219 只中）、**32 个 (ETF×日)**，|差| 合计 **28.72 亿**，最大 **7.32 亿**（159832 2022-03-09）。
- 反映到产物：`etf-ranges` 有 **9 条** >1 亿（159832 5y −9.59 vs 修正 −2.27；159833 5y −8.60 vs −2.01；511580 5y 66.55 vs 68.65 …），即 §1 表里那 27 条"无法归类"。

**修法**（一行）：遍历改为按日期升序，或直接返回「最早的 `d > date`」对应的累计值：

```js
for (const [d, v] of [...m].sort((a, b) => a[0].localeCompare(b[0]))) if (d > date) return wan * v;
```
